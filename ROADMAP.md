# Tab module roadmap

Open and deferred work, and the findings of the audit pass that are recorded rather than fixed.

## Closed by the audit pass

The module is unwired (see below), so none of these was reachable from a user action in this tree. They are recorded because the state they describe is what a consumer wiring the module up would have met.

- **`content` returned a promise that could never settle.** The getter built a promise whose executor returned the tables instead of resolving with them, so nothing ever called `resolve`. `DocumentResource` declares the property and core's own base class answers a settled `nullPromise`, which makes the override strictly worse than what it replaced: a consumer awaiting `resource.content` waited for the life of the page. The interface's own viewer reads `tables` rather than `content`, which is why the module could be used at all.
- **A table reporting its own activation stored a boolean as the active table.** The `isActive` monitor passed the property's new value — `true` — to `_setPropertyValue('activeTable', …)` rather than the table it came from. `activeTable` then answered `true` where its type promises a table or null, and the deactivation branch compared `this._activeTable?.id` against a boolean, so clearing never fired and the table stayed active for good.
- **The monitor only deactivated the tables added in the same call.** It closed over that call's arguments rather than the resource's tables, so two tables added by separate `addTables` calls could both be active — a state the `activeTable` setter cannot produce.
- **The main properties were keyed by their own values.** The navigator renders a `getMainProperties` entry by translating the map key with the value as its parameters, and this resource keyed each entry by the count as a string with the message inside the value. Two properties were the result: a bare number in place of "2 tables", and a collision whenever the table and study counts matched, which dropped one of the two entries. The `icon` and `title` fields the value carried are read by nothing.
- **Removing one subcontext removed every other child resource.** The child list was rebuilt from the remaining subcontexts, although `addSubcontexts` appends to whatever is already there, so any child the resource had acquired another way was dropped by a call that named one subcontext.
- **A row mutation resolved a section by position and wrote it back by name.** The five row methods accept an index or a name, clone the section they resolve, and replaced *every* section carrying the clone's name. Addressing by index therefore wrote through a different key than it read, and a table given two sections of one name had both replaced with the one copy that was edited. Resolution and write-back now share the position.
- **A falsy cell skipped its type check.** The validator read `row[i]?.value || null` and treated the result as an empty cell, so a zero, an empty string or a false passed validation whatever the column's content type was, while every other value was checked. The coalescing belongs on the cell, which is the thing that can be absent.
- **A table shared its column configuration with its caller.** The constructor stored the array it was given, and the property setters replace an array's contents in place, so writing a table's configuration rewrote the caller's array — and the configuration of every other table built from it. The suite found this one: a fixture shared between two tables was mutated out from under the tests that ran next.
- **The tables a load built were never monitored.** `loadStudyData` pushed each one straight into the array and dispatched the property change by hand, so it skipped `addTables` — the method that registers the active-state monitor on a table. Those are the only tables a resource loaded from a worker ever has, which made the whole active-table mechanism, defects above included, unreachable for every real resource: activating one table neither deactivated the others nor reached `activeTable`. Found by the clean-slate pass, after the two defects in the mechanism itself had already been fixed.
- **A second load started while the first was in flight.** Nothing guarded re-entry, and the resource's own activation listener can fire again before the first setup is answered, since it gates on a service that is not ready yet. Two setup commissions were the result, each building the tables of its reply, and the second `_initWaiters` call replaced the setup waiter list — leaving everything that had joined the first load waiting on a list nothing would notify. A load in flight is now joined.
- **Neither of the service's own commissions released its entry.** `handleMessage` intercepts `save-annotations` and `setup-worker` before the base class sees them, and the base class is what drops the map entry; nothing dropped these, so the service kept a resolve and reject closure pair for every commission it had ever sent. Labels are saved on every change to them.
- **A refused setup rejected the promise the resource reads as a result.** `loadStudyData` branches on `response.success` with no rejection handler, so a worker that refused the setup produced an unhandled rejection and left the resource in its loading state with nothing logged. The setup now resolves the failure carrying the worker's reason, which is what puts the resource in the error state.
- **A setup with no worker to post to resolved `null`.** `GenericService._commissionWorker` answers a resolved `null` when there is no worker — the state after a shutdown — so `response.success` threw a `TypeError` on a type that promised an object. The same path left the `setup-worker` waiters unnotified, which is what `initialSetup` resolves from: every later call awaiting it would have waited for the session.
- **The settings snapshot was read through an unguarded global.** `window.__EPICURRENTS__.RUNTIME` threw a `TypeError` for a module used outside an application, before any of the reporting above could apply.
- **A refused save from a label change was an unhandled rejection.** The property-change handler awaited `saveAnnotations` with no catch, and that call has no caller to report to. `saveAnnotationsToDataset` keeps rejecting, because its own documented contract is to, and it has a caller that can act on it.
- **A missing worker read as a saved annotation.** `saveAnnotations` resolved the base class's `null`, which is indistinguishable from a save that succeeded.
- **The loader asked twice whether it had a worker**, the second check carrying a different message and unreachable.
- **The lint configuration was the ESLint 8 format** that ESLint 9 does not read. The local ESLint 8 did read it, which is the failure shape worth knowing: the script ran, reported two problems and exited non-zero, against a rule set of two rules. The family set reports 49 problems on the same sources.
- **The declared core range was `^1.0.0`** while the package type-checks clean against the 2.0.0 in the workspace. Everything it uses — `_releaseCommission` included, which this pass introduced — is in the published 2.0.0, confirmed against its tarball, so the range is now `^2.0.0` and this package is not among those whose range has to move again when core releases `_validate`.
- **`test-runner.js` and `TEST_DOCUMENTATION.md`** described a Jest setup the package does not have, and the runner printed "All TypeScript types compile correctly" and "Unit tests are ready to run with Jest" without compiling or running anything. The one real test file covered the tables and the active table of one class, through a mocked service.
- **A `.env.example`** declaring two variables that no file in the repository reads, and an empty `shims.d.ts` holding nothing but its own header.

## The module is unwired

Both halves of it exist and nothing joins them. The package is here and builds; the interface carries a `tab` UI module with a viewer, controls and a store module. What is missing is the builder's own registrar — there is no `setup/modules/tab.ts`, so no profile can name the modality and no edition ships it, which `setup/registry.ts` and `profiles/full.mjs` both record in a comment.

The piece that decides the order is the worker. This package ships none: the service drives one the consumer registers with its study importer, under the key `tab-tab`, and the commission protocol it has to answer is in the README. Until something provides one, a registrar would compose a modality whose resource cannot load. So the sequence is a worker first, then the registrar, then a profile.

The package is not published, so none of its surface is a commitment yet. `getRows` and `addSections` are called by nothing, here or in the interface.

## What no test covers

The suite drives the real resource, table, service and loader, with the worker as the only double, so what is left out is what needs the worker to be real.

**The protocol itself.** The double answers what the service asks for, which makes it the executable form of the README's table — and the statement of a contract rather than a check of one. Nothing verifies that a real worker, written to that table, satisfies the service; the first one written is what will say.

**The subcontext path end to end.** The resource hands a template to the resource module registered for its modality and the tests cover that dispatch, including the module that cannot build one. What they cannot cover is a real module building a real resource from a real template, because that needs another modality's package in this one's toolchain.

## Smaller things

- **`TaskResponse.error` is declared an `Error`** in core while every worker in the family posts a string into it; the message a structured clone can carry is a string, not an error. This service reports its own failures through `message`, which the type declares a string, and passes a worker-reported `error` through as the string it is. The declaration is core's to correct.
- **`getMainProperties` is declared to return `Map<string, string|number|null>`** in core, and no implementation anywhere answers that: core's own base class and resource collection both put parameter objects in the value, and the navigator casts through `unknown` to read them. The cast in the interface is the visible end of a type that was never updated, and correcting it is core's.
- **The subcontexts setter rebuilds the child list from its own value.** Adding a subcontext writes the child list twice — once directly, once through the setter — and the setter's version is the subcontexts alone. Nothing has gone wrong because the direct write happens first and the setter's check finds no change, but the two writes disagree about what a child resource is, and only the order keeps them apart.
- **`numTables` falls back to the count the study meta declared** whenever no loaded table carries rows, so a resource whose tables all turned out to be metadata reports the preliminary number rather than zero. That is the useful answer while loading and the wrong one afterwards, and nothing distinguishes the two states.
- **Changing a table's column configuration does not revalidate its sections.** Every row mutation is checked against the configuration and the `sections` setter checks a whole list, but the `configuration` setter checks nothing, so a narrower configuration leaves a table holding rows that no longer match it — and then refuses every later mutation, because the validator runs over the sections already there. Deciding between refusing the change and clearing the rows is what has not been settled, so it is recorded rather than fixed.
- **`replaceRows` with a start past the last row appends instead of refusing.** The delete count comes out negative, which `splice` reads as zero, and the insert position is clamped to the end. The range checks reject `end < start` and a negative start but not a start beyond the rows.
- **The loader asks for its worker under `tab-tab`**, the modality prefixed by the string `tab`. It is the key a consumer has to register, so it is documented rather than changed; a module that shipped its own worker would not need the key at all.
